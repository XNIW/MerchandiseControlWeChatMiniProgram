## Context and objective

Extend the existing read-only category and supplier pages with controlled create, rename, archive and supported restore workflows. When an entity is referenced, the server must apply the real replacement/clear policy atomically and emit complete product/category/supplier convergence signals.

## Dependencies and files to read

- WMP-017 and WMP-018 product relation contract.
- Admin category/supplier services, permissions, RLS, audit and sync-event aggregation.
- Android deletion strategies: delete-if-unused, replace-existing, create-and-replace and clear assignments, only where the Admin ADR selects the same supported semantics.
- Shared display text policy for category/supplier names and existing Mini lists/counts.

## In scope

- Search/list/detail plus create and rename for authorized users.
- Product counts, archive warning, replacement/clear choice according to the canonical policy, and supported restore.
- One server-side transaction for reassignment plus archive; audit and standard sync events for every affected entity set.
- Viewer/read-only, saving, offline/retry, conflict and stale-count handling.

## Out of scope

- Client-side reassignment loops, hard delete, unbounded affected-product downloads, guessed replacement algorithms or role-derived write permission.
- Product field editing beyond category/supplier assignment and Excel import.

## Files potentially involved

- Mini category/supplier list/detail/form pages, typed mutation client, cache invalidation and locale dictionaries.
- Admin category/supplier canonical services, thin Mini routes, transaction/RLS/audit/sync tests.

## Acceptance criteria

- [ ] Create and rename use the shared display normalization and server-enforced case-insensitive uniqueness.
- [ ] Viewer and unauthorized/suspended/revoked users cannot create, rename, archive, restore or replace.
- [ ] Archive shows an authoritative affected-product count and requires the canonical replacement/clear decision when the entity is referenced.
- [ ] Replacement, relation changes and archive commit in one server transaction or fail without an intermediate inconsistent state.
- [ ] Every touched product and category/supplier remote ID is represented by complete standard sync-event entity IDs; repeated delivery is idempotent.
- [ ] Restore, when supported by the real schema, clears the archive marker on the same remote identity and rehydrates clients.
- [ ] Conflict/stale-count errors preserve the user decision and force a fresh authoritative preview before retry.
- [ ] List/detail/product caches and safe mutation history refresh after success without full-catalog download or N+1 requests.
- [ ] Tests cover create/rename/duplicate, unused archive, referenced replacement/clear, restore, viewer, shop A/B, suspension, concurrency, replay and rollback.

## Risks and remaining problems

- A stale product count can permit a replacement decision against changed data unless count and apply share an expected revision/transaction.
- Large affected sets require bounded server aggregation and chunk-complete sync events, not client loops.
- Name collisions after normalization and restore-versus-new-name races must fail closed.
- The exact restore capability must come from the schema/ADR; it cannot be invented from local mobile cache behavior.
- Active category/supplier fetches and replacement choices are currently bounded to 100 rows; production-scale behavior needs explicit review.
